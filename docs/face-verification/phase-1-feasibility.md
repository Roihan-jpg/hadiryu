# Face Verification — Phase 1: persiapan dan uji kelayakan

Status: studi dokumentasi, 2026-10-01. Belum ada implementasi, hasil benchmark perangkat, pemilihan model final, atau enforcement. Phase 1 ini adalah tahap persiapan yang disetujui pengguna; berbeda dari penamaan "Phase 1 — Camera Foundation" pada `FACE_VERIFICATION_PLAN.md`. Tahap kamera bergeser ke fase implementasi berikutnya.

## Baseline project dan batas fitur

Runtime saat ini: Angular standalone di `apps/web`, kontrak Zod di `packages/contracts`, Express di `apps/api` yang dilayani Cloudflare Worker satu origin (`worker/index.ts`), serta PostgreSQL Supabase. Sesi `app_sessions`/`app_accounts` adalah auth aplikasi, bukan Supabase Auth. `AttendanceService` mengirim `LocationInput` ke `GET /api/attendance/today`, `POST /api/attendance/check-in`, dan `POST /api/attendance/checkout`; Pulang Awal `POST /api/early-departure-requests` juga melakukan checkout. Keputusan tanggal Jakarta, waktu server, izin, geofence dan penulisan tetap backend. Satpam tidak masuk lingkup Face Verification pertama.

Baseline keputusan audit: Guru saja; enrollment mandiri setelah login; template dihapus saat akun dinonaktifkan; inference privat di luar Worker; pilot non-enforcing sebelum kebijakan wajib. Tidak satu pun diaktifkan Phase 1. `PRD.md` masih mengecualikan face dari MVP berjalan; perubahan itu sengaja belum dihapus.

## Requirement teknis private inference service

1. Service hanya dapat dipanggil oleh Express/Worker melalui endpoint privat yang diautentikasi machine-to-machine, TLS, allowlist/network restriction, rotasi secret, request ID, dan timeout ketat. Tidak menerima browser-origin CORS maupun akses Supabase service key. Pilihan mekanisme private connectivity, hosting, dan otentikasi spesifik adalah **OPEN DECISION**.
2. Input internal harus dibatasi dengan schema: `verificationId`, aksi (`CHECK_IN | CHECKOUT | EARLY_DEPARTURE`), urutan frame terkompresi, challenge spec server, identitas template opaque, dan versi model/threshold yang dikonfigurasi server. Template/embedding tidak dikirim ke browser. Metadata client (landmark, timestamp, quality) hanya petunjuk; service memeriksa ulang wajah tunggal, kecocokan, dan PAD dari bukti visual. Kekuatan verifikasi challenge berbasis frame statis vs klip singkat adalah **OPEN DECISION** setelah attack test.
3. Respons internal berisi status teknis terstruktur (`ONE_FACE`, `PAD_PASS`, `MATCH_PASS`, `INCONCLUSIVE`/error), skor mentah, versi model, timing per tahap, tanpa status absensi. Express menerapkan threshold dan keputusan final; model tidak boleh langsung memberi izin absensi.
4. Service harus warm saat traffic, health/readiness probe memeriksa bobot termuat, model checksum/version dipin, preprocessing deterministik dan terdokumentasi, tidak melakukan auto-download model saat request. Kapasitas, CPU/RAM minimum, GPU perlu/tidak, jumlah worker, dan warm-up time adalah **OPEN DECISION** sampai profiling.
5. Batasi jumlah frame, resolusi, MIME, byte terkompresi, byte ter-decode, durasi media, dekompresi, dan concurrent inference; tolak input rusak/berlebih sebelum inferensi. Frame mentah tidak disimpan/log; hasil audit hanya keputusan, versi, durasi, kategori gagal, dan request ID. Kebijakan consent, retensi, enkripsi template dan recovery akun harus disetujui sebelum enrollment.
6. Timeout/error inference tidak boleh diinterpretasikan sebagai `PASS`. Pada pilot non-enforcing, jalur lama tetap sah dan hasil face hanya observasi terpisah; pada enforcement kelak harus ada kebijakan fail-closed/fallback operasional tertulis. Target total UX 2–5 detik adalah target p95 yang belum terbukti, bukan SLA model.

## Batas kontrak yang akan diwujudkan pada fase implementasi

Kontrak ini adalah spesifikasi semantik, **belum endpoint aktif atau Zod schema**. Implementasi wajib membuat schema di `packages/contracts` sebelum menghubungkan Angular dan Express. JSON camelCase, PostgreSQL snake_case, `ApiError` existing tetap berlaku.

| Boundary | Data masuk | Data keluar / otoritas |
| --- | --- | --- |
| Angular → Express `POST /api/attendance/face/session` (rencana) | `action` enum; cookie HttpOnly/anti-CSRF existing. Tidak menerima `userId`, waktu resmi, atau challenge pilihan browser. | `sessionId`, challenge acak server, `expiresAt`, batas media. Server validasi role Guru, status akun/aksi, rate limit, dan simpan state single-use. |
| Angular → Express `POST /api/attendance/face/verify` (rencana) | `sessionId`, frame/klip berurutan dan ukuran terbatas, `LocationInput`, `idempotencyKey`; optional observasi client tidak dipercaya. `clientTimestamp` dari plan tidak dipakai untuk keputusan waktu. | Respons mengikuti record/status absensi existing plus status verifikasi aman; Express tetap menentukan waktu, challenge, geofence, aturan/domain, idempotency, dan satu record per tanggal. |
| Express/Worker → private inference | `verificationId`, action, media yang sudah divalidasi, challenge spec server, referensi template opaque atau embedding yang diambil aman, model version. Kanal service-to-service saja. | Skor PAD/match, one-face, kualitas/ketidakpastian, timing dan versi; tidak ada `attendanceSuccess`, write DB, atau lokasi kecuali kebutuhan teruji. |
| Express → PostgreSQL | Session/challenge, template biometrik terenkripsi, hasil audit minimal, serta pencatatan absensi via aturan existing. | DB mempertahankan unique `(teacher_id, work_date)`, timestamp immutable, idempotency, dan RLS. Migration dan retensi belum dirancang pada Phase 1. |

Session harus user/action/workDate-bound, acak kuat, singkat, satu kali pakai secara atomik; replay request yang sama ditangani idempotency tanpa inferensi/tulis kedua. Replay dengan payload berbeda ditolak. Detail semantik status HTTP dan bentuk final payload/error adalah **OPEN DECISION** untuk kontrak Zod fase berikut. `EARLY_DEPARTURE` membutuhkan integrasi khusus agar jalur Pulang Awal tidak menjadi bypass; tidak digabung dengan checkout biasa tanpa mempertahankan alasan/lampiran/approval.

## Rencana benchmark Android dan laptop

Tujuan: membuktikan atau menolak kelayakan target total p95 2–5 detik tanpa melemahkan batas keamanan. Benchmark dilakukan **sebelum** pemilihan model, threshold, atau enforcement, dengan artefak versi/checksum tetap dan data subjek yang memiliki consent. Jangan memakai data wajah produksi tanpa kebijakan privasi.

1. Catat matriks perangkat: Android rendah-menengah dan menengah (model, SoC, RAM, versi Android/Chrome, kamera, resolusi), laptop kelas kantor (CPU/RAM/OS/browser/kamera), serta spesifikasi host inference CPU (dan GPU bila dibandingkan). Jalankan Wi-Fi stabil, seluler normal, seluler lemah/latency tinggi; catat RTT/throughput, pencahayaan terang/redup/backlight, kacamata/hijab bila relevan dan disetujui, posisi muka, serta warm/cold service.
2. Gunakan subjek/identitas dan sesi berbeda yang disetujui. Pisahkan enrollment set, genuine attempts, impostor attempts, serta spoof print, layar ponsel/laptop, video replay, dan bila aman mask. Hindari frame orang yang sama di train/tune/test; hindari tuning pada final holdout. Catat denominator, interval kepercayaan, dan hasil per kondisi/perangkat. Jumlah sampel/target FAR-FRR/APCER-BPCER yang bermakna statistik adalah **OPEN DECISION** bersama pemilik risiko; dataset kecil tidak boleh diklaim aman.
3. Ukur `performance.now()` di browser untuk permission/camera-ready, face+landmark/quality, challenge, encode, upload, response. Server mengukur auth/session, parse/decode, inference queue, detector, PAD, embedding/match, geofence/domain, DB write; korelasikan request ID. Laporkan p50/p95/p99, cold/warm, timeout, retry, dan `time-to-attendance-confirmed`, bukan hanya waktu inferensi.
4. Catat ukuran tiap frame dan total request bytes (wire, setelah kompresi dan setelah decode), resolusi/format/quality, serta upload duration. Ukur CPU%, peak RSS/heap, jumlah thread, throughput dan queue depth pada host inference; browser Android/laptop mengukur durasi main-thread/long task, memori bila tersedia, baterai/termal sebagai observasi. Jalankan cold-start dan concurrency 1/5/10; setiap konfigurasi diulang cukup untuk persentil stabil dan variasi dilaporkan.
5. Identitas: hitung FAR = impostor accepted / impostor attempts dan FRR = genuine rejected / genuine attempts pada threshold yang dikunci di validation set; laporkan ROC/DET dan TAR@FAR sesuai ukuran sampel. PAD: APCER = attack accepted / attack attempts, BPCER = bona fide rejected / bona fide attempts, ACER rata-ratanya; pisahkan tipe serangan. End-to-end laporkan false attendance accept/reject termasuk challenge+geofence, namun jangan mengaburkan metric komponen.
6. Jalankan ablation: SFace FP32/int8 jika artefak/lisensi jelas, PAD MN3 ONNX vs OpenVINO hanya bila hasil setara; jumlah/resolusi frame dan quality JPEG/WebP; single/parallel geofence; pemanasan model. Validasi kesetaraan skor sebelum mengubah runtime/kuantisasi. Semua rekomendasi berdasarkan hasil lokal, bukan angka publik dataset lain.

### Acceptance gate sebelum Phase 2

- Dokumen Phase 1, ADR, PRD/TechDesign dan task state konsisten; tidak ada source/runtime/schema/dependency berubah.
- Tiap kandidat mempunyai catatan terpisah tentang lisensi source, bobot, batas komersial, runtime, ukuran, CPU/RAM (atau **OPEN DECISION** bila belum terukur), dan ONNX.
- Spesifikasi benchmark mencakup Android/laptop, cold/warm, kondisi kamera/jaringan, latency end-to-end/komponen, FAR/FRR, APCER/BPCER, bytes, CPU/RAM, dan serangan replay.
- Batas kontrak memisahkan browser, API keputusan final, dan inference privat; jalur Pulang Awal serta Satpam tidak terlewat.
- Phase 2 **boleh mulai hanya dengan persetujuan scope implementasi**; pemilihan model final/enforcement tetap menunggu hasil benchmark, legal, privasi, dan attack test. Target 2–5 detik tidak diklaim tercapai dari dokumen ini.

## OPEN DECISION prioritas

1. Hak komersial dan provenance dataset untuk bobot SFace/anti-spoof-mn3 (dan izin model MiniFASNet jika diteruskan); legal review dan pin checksum versi.
2. Host/region, private connectivity, service auth, budget, kapasitas, CPU/GPU, cold-start, timeout, dan SLA inference.
3. Persetujuan consent/retensi/enkripsi/penghapusan template, recovery ketika enrollment mandiri keliru atau akun diretas, serta aksesibilitas/fallback bagi Guru yang tidak dapat menggunakan kamera.
4. Format bukti temporal yang memadai untuk challenge dan anti-replay; ukuran/frame count; threshold FAR/FRR/PAD serta sample size dari evaluasi lapangan.
5. Semantik final API/error/idempotency/session storage dan urutan interaksi geofence–inference, khususnya Pulang Awal dan pilot non-enforcing.
